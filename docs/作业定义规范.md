## V1 兼容性：机器契约保持不变

JobOps、Job Definition（作业定义）和 Job Definition Version（作业定义版本）是本规范的产品与概念名称。为保持 V1 客户端、存储、脚本和浏览器状态的兼容性，下列既有机器字面量**有意保留**，不得因本次术语迁移而改名或全局替换：

- REST 路径：`/api/bots`（及其既有子路径）；
- 存储资源与字段：`bots`、`bot_versions`、`bot_id`、`bot_code`、`bot_version_id`、`bot_snapshot`；
- 协议、环境变量和错误码中的 `BOT_*` 代码；
- SDK 与脚本文件用途：`bot_sdk`、`bot_script`；
- 所有既有 `bot_*` ID，以及浏览器存储键 `botops-*`。

这些字面量表示已发布的 V1 合同，而非新的产品术语。它们在 API、数据库、协议、脚本、示例和兼容层中必须保持精确拼写；说明性文字一律使用“作业定义”或“作业定义版本”。

<a id="job-definition-model"></a>
## 领域模型

### Job Definition（作业定义）

`Job Definition（作业定义）` 是自动化能力的逻辑定义，不是脚本执行实例，也不是一次执行。

示例：

```text
OEM-APPROVAL-SUBMIT
APPROVAL-STATUS-QUERY
ANNOUNCEMENT-CRAWL
INVENTORY-SYNC
PRICE-MONITOR
FILE-PARSE
```

Job Definition（作业定义） 可以理解为：

```text
Job Definition（作业定义） = 编码 + 业务用途 + 输入参数定义 + 默认输入来源 + 默认运行配置 + 默认运行要求
```

`Job Definition（作业定义）.code` 是 Job Definition（作业定义） 稳定、面向人的标识；创建后不可修改。

具体脚本及其入口不直接作为 Job Definition（作业定义） 的逻辑定义，而是通过 Job Definition Version（作业定义版本） 进行版本化管理：

```text
Job Definition Version（作业定义版本） = source_file_id + entrypoint + input_params_schema + default_input_source + default_config + default_requirements
```

---

### Job Definition Version（作业定义版本）

`Job Definition（作业定义）` 是自动化能力的逻辑定义，描述编码、输入参数定义、默认输入来源、默认运行配置和默认运行要求；`Job Definition Version（作业定义版本）` 是该 Job Definition（作业定义） 的一个可执行、可发布版本，保存具体脚本包、入口文件以及这些字段在该版本中的快照。

一个 `Job Definition（作业定义）` 可以拥有多个 `Job Definition Version（作业定义版本）`，但一个 `Job Definition Version（作业定义版本）` 只能属于一个 `Job Definition（作业定义）`。版本通过 `bot_id` 归属 Job Definition（作业定义）；Job Definition（作业定义） 通过 `current_version_id` 指向当前默认版本。`current_version_id` 可以为空，也只能指向该 Job Definition（作业定义） 下一个 `published` 的 Job Definition Version（作业定义版本）；同一 Job Definition（作业定义） 同一时刻最多一个版本的 `is_current=true`。

对象关系：

| 对象 | 关系字段 | 作用 |
|---|---|---|
| `Job Definition（作业定义）` | `id`、`current_version_id` | 逻辑上的自动化能力；不直接代表一次执行 |
| `Job Definition Version（作业定义版本）` | `bot_id`、`version`、`is_current` | Job Definition（作业定义） 的具体可执行版本；同一 Job Definition（作业定义） 内按版本号递增 |
| `Task` | `bot_id`、`bot_version_id`、`bot_snapshot` | 创建时解析并冻结实际使用的 Job Definition Version（作业定义版本） |
| `Schedule` | `bot_id`、可选 `bot_version_id` | 未固定版本时触发时解析 current version；固定版本时使用指定的 published 版本 |

版本关系和运行解析：

```text
Job Definition（作业定义）
 ├── Job Definition Version（作业定义版本）(version=1, status=draft)
 ├── Job Definition Version（作业定义版本）(version=2, status=published, is_current=false)
 └── Job Definition Version（作业定义版本）(version=3, status=published, is_current=true)
         └── Job Definition（作业定义）.current_version_id = version=3

创建 Task
 ├── 指定 bot_version_id：使用指定的 published 版本
 └── 未指定 bot_version_id：使用 Job Definition（作业定义）.current_version_id

创建后的 Task
 └── 冻结 bot_id + bot_version_id + bot_snapshot
```

`Job Definition（作业定义）.status` 和 `Job Definition Version（作业定义版本）.status` 属于不同状态命名空间，不能共用状态迁移规则。发布新版本或更新 Job Definition（作业定义） 只影响之后的版本解析，不会改写已经创建的 Task；Task 的完整快照字段仍以 [Task执行规范.md](Task执行规范.md#task-model) 为准。

### Job Definition Version（作业定义版本） 状态与版本原则

`Job Definition Version（作业定义版本）.status` 表示版本自身的发布状态；`is_current` 表示该版本是否是所属 Job Definition（作业定义） 当前默认使用的版本。两者不是同一个状态维度。

作业定义版本状态：

| 值 | 含义 |
|---|---|
| `draft` | 已创建但未发布；不会被默认 Task / Schedule 使用 |
| `published` | 曾经或正在作为可运行版本；历史 published 版本仍可通过 `bot_version_id` 指定执行 |

<a id="job-definition-version-lifecycle"></a>
## Job Definition Version（作业定义版本） 生命周期与版本解析

### 生命周期原则

```text
影响执行行为的字段变化时创建 Job Definition Version（作业定义版本）
创建版本默认 status=draft，不修改 Job Definition（作业定义）.current_version_id
只有 publish 才会把该版本设为 current
Task 创建时记录 bot_version_id，并复制 bot_snapshot
Job Definition（作业定义） 更新不影响历史 Task
同一 Job Definition（作业定义） 同一时刻最多一个 is_current=true
```

### 版本解析与运行关系


```text
默认创建 Task（未指定 bot_version_id）
  -> 使用 Job Definition（作业定义）.current_version_id
  -> 若 current_version_id 为空，返回 HTTP 422，REST error.code=BOT_VERSION_REQUIRED（见 [错误标识注册表](错误标识注册表.md#error-registry) 表 A）

指定 bot_version_id 创建 Task
  -> 允许使用任意 published 版本（含当前与历史）
  -> draft 不可被 Task / Schedule 引用

Schedule.bot_version_id 为空
  -> 每次触发使用当时的 current_version_id

Schedule.bot_version_id 有值
  -> 固定使用该 published 版本，不受后续 publish 影响

Job Definition（作业定义） enable
  -> 要求已有 current_version_id，否则 enable 返回 HTTP 422，REST error.code=BOT_VERSION_REQUIRED
```

`BOT_VERSION_REQUIRED` 的稳定定义见 [REST 错误码注册表](错误标识注册表.md#rest-errors)。

`can_run` 计算：

```text
Job Definition（作业定义）.status == enabled
且 current_version_id 不为空
且当前用户有运行权限
```

### Source File 前置条件

V1 的脚本来源实际实现为 `upload`。创建或发布 Job Definition Version（作业定义版本） 时，`source_file_id` 必须引用通过 [Source File API](./源文件.md#source-file-api) 上传、用途为 `bot_script` 且状态为 `ready` 的文件。Source File 的上传、下载、删除和存储边界不在本文件中重复定义。

### 跨层待对齐项

Job Definition Version（作业定义版本） 与 Task 快照、Schedule 字段、Source File 引用生命周期之间的未闭环问题分别由 [`ALIGN-001`](待对齐问题.md#align-001)、[`ALIGN-002`](待对齐问题.md#align-002) 和 [`ALIGN-010`](待对齐问题.md#align-010) 跟踪；本文件不自行裁决这些问题。

<a id="create-job-definition"></a>
### 创建 Job Definition（作业定义）

```http
POST /api/bots
```

请求字段：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---:|---|---|
| `code` | string | 是 | - | 稳定唯一、面向人的 Job Definition（作业定义） 标识 |
| `description` | string | 否 | `null` | 描述 |
| `category` | string | 否 | `null` | 分类 |
| `tags` | array<string> | 否 | `[]` | 标签 |
| `entrypoint` | string | 是 | - | 入口文件，例如 `main.py` |
| `script_source` | string | 是 | `upload` | 脚本来源 |
| `source_file_id` | string | 否 | `null` | 已通过 `POST /api/files`（purpose=`bot_script`）上传的脚本包 ID，见 [Source File API](./源文件.md#source-file-api) |
| `default_input_source` | string | 是 | - | 默认输入来源 |
| `input_params_schema` | object | 否 | `{}` | 参数 schema |
| `default_config` | object | 否 | `{}` | 默认配置 |
| `default_requirements` | object | 否 | `{}` | 默认运行要求 |
| `publish` | boolean | 否 | `true` | 提供 `source_file_id` 时，是否立即发布自动创建的 version=1；未提供文件时忽略 |

创建规则：

```text
提供 source_file_id：创建 Job Definition（作业定义） + version=1 的 Job Definition Version（作业定义版本）
publish=true：version=1 立即成为 current version
publish=false：version=1 保持 draft，Job Definition（作业定义）.current_version_id=null
未提供 source_file_id：只创建 Job Definition（作业定义） 元数据，后续通过 Job Definition Version（作业定义版本） API 创建并发布版本
```

第一版脚本来源实际实现：

```text
upload
```

预留：

```text
git
image
inline
```

<a id="update-job-definition"></a>
### 更新 Job Definition（作业定义）

```http
PATCH /api/bots/{bot_id}
```

允许直接更新的 Job Definition（作业定义） 元数据字段：

```text
description
category
tags
```

以下执行字段不允许通过 PATCH 直接修改：

```text
entrypoint
source_file_id
script_source
default_input_source
input_params_schema
default_config
default_requirements
```

需要修改执行字段时，必须调用：

```http
POST /api/bots/{bot_id}/versions
```

创建新的 draft Job Definition Version（作业定义版本），确认后再通过 publish 接口切换 current version。

规则：

```text
PATCH Job Definition（作业定义） 不隐式创建或发布 Job Definition Version（作业定义版本）
影响执行行为的字段变化必须走 Job Definition Version（作业定义版本） create + publish
Job Definition（作业定义） 更新和版本发布均不影响历史 Task
已经创建的 Task 使用创建时的 bot_snapshot
code 是稳定、面向人的标识，第一版不允许修改；如后续开放，必须保证唯一并记录审计
```

```http
POST /api/bots/{bot_id}/run
```

```http
POST /api/tasks
```

Query 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | 按 `draft`、`enabled`、`disabled`、`archived` 过滤 |
| `category` | string | 按分类过滤 |

```text
id, code, category, status, current_version_id,

```

<a id="get-job-definition"></a>
### 查询 Job Definition（作业定义） 详情

```http
GET /api/bots/{bot_id}
```

响应返回完整 Job Definition（作业定义） 共享对象，并可附带：

```text
current_version
schedules_count
recent_tasks_count
can_run
can_edit
```

`current_version` 只返回 `Job Definition（作业定义）.current_version_id` 指向的那个 Job Definition Version（作业定义版本），不返回历史版本列表，也不返回其他 `published` 或 `draft` 版本。若 `current_version_id` 为空，则 `current_version` 返回 `null`。

需要查询全部版本时，调用：

```http
GET /api/bots/{bot_id}/versions
```

需要查询指定版本时，调用：

```http
GET /api/bots/{bot_id}/versions/{version_id}
```

`can_run`、`can_edit` 是后端根据 Job Definition（作业定义） 状态和当前用户权限计算的操作能力，不是数据库持久字段。

<a id="toggle-job-definition-status"></a>
### 启用 / 禁用 Job Definition（作业定义）

```http
POST /api/bots/{bot_id}/enable
POST /api/bots/{bot_id}/disable
```

请求体默认为空。响应返回：

| 字段 | 说明 |
|---|---|
| `id` | Job Definition（作业定义） ID |
| `status` | 操作后的 作业定义状态 |
| `updated_at` | 状态更新时间 |

规则：

```text
禁用 Job Definition（作业定义） 不影响已经创建的 Task
禁用 Job Definition（作业定义） 后不能创建新的手动/API Task
禁用 Job Definition（作业定义） 后 Schedule 到点应生成 skipped 的 ScheduleRun
启用 Job Definition（作业定义） 要求 current_version_id 不为空，否则返回 HTTP 422，REST error.code=BOT_VERSION_REQUIRED（注册见 [错误标识注册表](错误标识注册表.md#error-registry) 表 A）
启用 Job Definition（作业定义） 不会自动补跑之前跳过的 ScheduleRun
```

<a id="create-job-definition-version"></a>
#### 创建 Job Definition Version（作业定义版本）

```http
POST /api/bots/{bot_id}/versions
```

请求字段：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---:|---|---|
| `source_file_id` | string | 是 | - | 已通过 `POST /api/files`（purpose=`bot_script`）上传的脚本包 ID，详见 [Source File API](./源文件.md#source-file-api) |
| `entrypoint` | string | 是 | - | 入口文件，例如 `main.py` |
| `input_params_schema` | object | 否 | `{}` | 参数 JSON Schema |
| `default_input_source` | string | 是 | - | 默认输入来源 |
| `default_config` | object | 否 | `{}` | 默认配置 |
| `default_requirements` | object | 否 | `{}` | 默认运行要求 |
| `change_note` | string | 否 | `null` | 版本说明 |
| `publish` | boolean | 否 | `false` | 为 `true` 时创建后立即发布为当前版本，等价于创建成功后再调一次 publish |

创建成功后的默认状态：

```text
status = draft
is_current = false
Job Definition（作业定义）.current_version_id 不变（除非 publish=true）
version = 该 Job Definition（作业定义） 已有最大版本号 + 1
```

响应返回 `Job Definition Version（作业定义版本）` 共享对象。

```json
{
  "data": {
    "id": "botver_003",
    "bot_id": "bot_oem_approval",
    "version": 3,
    "status": "draft",
    "is_current": false,
    "source_file_id": "file_script_xxx",
    "entrypoint": "main.py",
    "created_at": "2026-07-15T12:00:00Z"
  },
  "request_id": "req_xxx"
}
```

规则：

```text
创建版本本身不会让 Schedule / 默认 Task 立刻切到新脚本
避免上传中间版本、调试包被定时任务误用
需要生效时调用 publish，或创建时显式 publish=true
```

#### 查询 Job Definition Version（作业定义版本） 列表 / 详情

```http
GET /api/bots/{bot_id}/versions
GET /api/bots/{bot_id}/versions/{version_id}
```

列表 Query：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | `draft` / `published` |
| `is_current` | boolean | 是否只看当前版本 |
| `sort` | string | 默认 `-version` |

列表项至少返回：

```text
id, bot_id, version, status, is_current,
entrypoint, change_note, created_by, created_at,
published_at, published_by
```

<a id="job-definition-version-publish"></a>
#### 发布 Job Definition Version（作业定义版本）

```http
POST /api/bots/{bot_id}/versions/{version_id}/publish
```

将指定版本发布为 Job Definition（作业定义） 的**当前版本**。这是第一版更新 `current_version_id` 的唯一正式写路径（创建时 `publish=true` 内部也走同一套逻辑）。

请求字段：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---:|---|---|
| `change_note` | string | 否 | `null` | 可补充发布说明；不修改版本创建时的 change_note，可写入 Job Definition（作业定义） 发布审计日志，不得写入 `task_events` |

处理步骤（同一事务）：

```text
1. 校验 version 属于该 bot_id，且 source_file_id 对应文件 status=ready
2. 将该 Job Definition（作业定义） 下原 is_current=true 的版本置为 is_current=false（status 保持 published）
3. 目标版本：
     status = published
     is_current = true
     published_at = now
     published_by = 当前用户
4. Job Definition（作业定义）.current_version_id = 目标 version_id
5. 同步 Job Definition（作业定义） 执行快照字段：
     entrypoint / script_source / default_input_source / input_params_schema /
     default_config / default_requirements
     必须取自该 Job Definition Version（作业定义版本），并与 current_version_id 在同一事务中更新
```

可发布条件：

```text
Job Definition（作业定义） 未 archived
目标版本存在且属于该 Job Definition（作业定义）
目标版本 source_file_id 有效
目标版本可以是 draft，也可以是历史 published（用于回滚到旧版本）
```

幂等：

```text
若目标版本已经 is_current=true：
  返回 200 与当前 Job Definition Version（作业定义版本） / Job Definition（作业定义） 摘要
  不重复写审计副作用（可只刷新 updated_at 或不改）
```

响应：

```json
{
  "data": {
    "bot": {
      "id": "bot_oem_approval",
      "current_version_id": "botver_003",
      "status": "enabled",
      "updated_at": "2026-07-15T12:05:00Z"
    },
    "version": {
      "id": "botver_003",
      "version": 3,
      "status": "published",
      "is_current": true,
      "published_at": "2026-07-15T12:05:00Z",
      "published_by": "user_001"
    },
    "previous_version_id": "botver_002"
  },
  "request_id": "req_xxx"
}
```

### 创建 Job Definition（作业定义） 与首个版本

创建 Job Definition（作业定义） 时携带 `source_file_id` 会创建 version=1；`publish` 决定是否立即发布。完整请求字段和规则见 [创建 Job Definition（作业定义）](#create-job-definition)，本节不再重复定义。
