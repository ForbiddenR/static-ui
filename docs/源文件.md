<a id="source-file-api"></a>
## Source File API 定稿

Source File 表示平台托管的输入类文件元数据，对应数据表 `source_files`。它是 Job Definition 脚本包、Task 输入文件、Schedule 固定输入文件的统一上传入口。

Source File 与 Artifact 的区别：

```text
Source File  用户/系统上传的输入文件（脚本包、Excel 输入等）
Artifact     任务运行产生的输出文件（截图、导出、回执等）
```

第一版：

```text
storage_backend = local
上传接口写入 Master 可访问的本地或共享存储
Worker 执行时由 Master/Worker 侧按权限拉取文件内容，不把可长期访问的 storage path 直接暴露给前端
```

### 接口索引

| 方法 | 路径 | 用途 | 详细说明 |
|---|---|---|---|
| `POST` | `/api/files` | 上传文件，创建 Source File | [上传文件](#upload-file) |
| `GET` | `/api/files` | 分页查询 Source File 列表 | [查询文件列表](#list-source-files) |
| `GET` | `/api/files/{file_id}` | 查询 Source File 元数据 | [查询文件详情](#get-source-file) |
| `GET` | `/api/files/{file_id}/download` | 下载文件内容 | [下载文件](#download-source-file) |
| `DELETE` | `/api/files/{file_id}` | 删除未被引用的文件 | [删除文件](#delete-source-file) |

第一版不提供：

```http
PATCH /api/files/{file_id}
POST  /api/files/{file_id}/copy
```

### 共享返回对象：SourceFile

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | string | 是 | Source File ID，例如 `file_xxx` |
| `name` | string | 是 | 平台内展示名；未传时默认使用原始文件名 |
| `original_name` | string | 是 | 上传时的原始文件名 |
| `content_type` | string | 是 | MIME 类型，例如 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| `size` | integer | 是 | 文件大小，字节 |
| `storage_backend` | string | 是 | 存储后端，第一版固定 `local` |
| `checksum` | string | 否 | 校验值，建议 `sha256:<hex>` |
| `purpose` | string | 是 | 文件用途，见下表 |
| `status` | string | 是 | `ready` / `deleted`；上传成功后为 `ready` |
| `created_by` | string | 是 | 上传人用户 ID 或 API token 主体 |
| `created_at` | string | 是 | 创建时间 |
| `updated_at` | string | 是 | 更新时间 |

`purpose` 取值：

| 值 | 含义 | 后续引用字段 |
|---|---|---|
| `bot_script` | Job Definition 脚本包，例如 zip | Job Definition / Job Definition Version 的 `source_file_id` |
| `task_input` | Task 输入文件，例如 Excel | Task 的 `input_file_id` |
| `schedule_input` | Schedule 固定输入文件 | Schedule 的 `input_file_id` |
| `other` | 其他输入文件 | 预留 |

<a id="file-categories"></a>
### 文件分类与使用边界

`SourceFile` 是统一的文件存储资源；业务语义由上传时必填的 `purpose` 决定。执行脚本和业务输入附件共用上传、下载、权限和存储机制，但不是同一种使用场景。

| 语义类别 | `purpose` | 关联字段 | 运行含义 |
|---|---|---|---|
| Job Definition 脚本包（Job Definition Script Package） | `bot_script` | `Job Definition` / `Job Definition Version.source_file_id` | 作为 Job Definition Version 的执行代码，配合 `entrypoint` 执行 |
| Task 输入文件（Input File） | `task_input` | `Task.input_file_id` | 作为 Task 输入提供给脚本，不作为代码执行 |
| Schedule 固定输入文件（Input File） | `schedule_input` | `Schedule.input_file_id` | Schedule 触发 Task 时作为输入文件，不作为代码执行 |
| 其他输入文件 | `other` | 仅在具体资源明确允许时使用 | 不能自动推断为脚本或通用附件 |
| Artifact 输出文件 | 不适用 | `artifact_id` | 任务运行产生的输出，不属于 SourceFile；完整定义见 [结果-产物-日志.md](结果-产物-日志.md#artifact-api) |

规则：

```text
上传 bot_script 只创建文件资源，不会自动执行脚本
Job Definition Version 必须在创建或发布时引用 purpose=bot_script 的 ready 文件
Task / Schedule 的 input_file_id 不得引用 purpose=bot_script
purpose=other 只有在目标资源明确允许时才可以引用，不是任意用途通配符
Artifact 由任务运行产生，不通过 Source File API 作为输入文件上传
```

```text
API 返回元数据，不返回 storage_key / 可直接访问的本地路径
storage_key 仅存数据库，供 Master / Worker 内部下载
下载必须走鉴权接口 GET /api/files/{file_id}/download
```

<a id="upload-file"></a>
### 上传文件

```http
POST /api/files
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---:|---|---|
| `file` | file | 是 | - | 文件本体 |
| `purpose` | string | 是 | - | `bot_script` / `task_input` / `schedule_input` / `other` |
| `name` | string | 否 | 原始文件名 | 展示名 |
| `idempotency_key` | string | 否 | `null` | 同一创建主体下防重复上传；各入口去重作用域与存储边界由 [`ALIGN-013`](待对齐问题.md#align-013) 跟踪 |

约束：

```text
purpose = bot_script     时，建议 content_type 为 zip / tar.gz 等脚本包格式
purpose = task_input     时，常见为 xlsx / csv / json
purpose = schedule_input 时，约束同 task_input
第一版单文件大小上限建议 100MB；超过平台配置的上传大小限制时返回 HTTP `413`，`error.code=PAYLOAD_TOO_LARGE`
第一版不做病毒扫描；可在后续版本增加异步扫描状态
```

请求示例（multipart 字段示意）：

```text
file=@approvals.xlsx
purpose=task_input
name=2026-07-15 审批清单
idempotency_key=upload-order-20260715-001
```

响应：

```json
{
  "data": {
    "id": "file_20260715_excel",
    "name": "2026-07-15 审批清单",
    "original_name": "approvals.xlsx",
    "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    "size": 18432,
    "storage_backend": "local",
    "checksum": "sha256:...",
    "purpose": "task_input",
    "status": "ready",
    "created_by": "user_001",
    "created_at": "2026-07-15T10:30:00Z",
    "updated_at": "2026-07-15T10:30:00Z"
  },
  "request_id": "req_xxx"
}
```

上传成功后，调用方把返回的 `id` 作为：

```text
创建 Job Definition / Job Definition Version 时的 source_file_id
创建 Task 时的 input_file_id
创建 Schedule 时的 input_file_id
```

典型链路：

```text
1. POST /api/files  (purpose=task_input)  -> file_id
2. POST /api/tasks  (input_source=file, input_file_id=file_id)
```

```text
1. POST /api/files  (purpose=bot_script)  -> file_id
2. POST /api/bots   (script_source=upload, source_file_id=file_id)
   或 POST /api/bots/{bot_id}/versions (source_file_id=file_id)
```

<a id="list-source-files"></a>
### 查询文件列表

```http
GET /api/files
```

Query 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `purpose` | string | 按用途过滤 |
| `created_by` | string | 按上传人过滤 |
| `q` | string | 搜索 name、original_name |
| `checksum` | string | 按校验值精确查询，便于去重排查 |

列表默认不返回已删除文件。列表项至少返回：

```text
id, name, original_name, content_type, size,
purpose, status, created_by, created_at
```

<a id="download-source-file"></a>
### 下载文件

```http
GET /api/files/{file_id}/download
```

规则：

```text
必须鉴权
校验当前用户是否有权访问该文件：
  - 上传者本人
  - 管理员
  - 引用该文件的 Job Definition / Task / Schedule 的授权访问者
响应头设置 Content-Type 与 Content-Disposition
不在元数据中直接返回可长期访问的 storage path 或未鉴权 URL
```

Worker 执行 Task 时，不走前端下载接口，而由 Worker 通过内部机制获取输入文件，并注入为环境变量：

```text
INPUT_FILE_PATH
```

<a id="delete-source-file"></a>
### 删除文件

```http
DELETE /api/files/{file_id}
```

规则：

```text
若文件仍被未归档 Job Definition Version / 未终态或近期 Task / 启用中 Schedule 引用，返回 409
未被引用时可删除
第一版采用软删除：status=deleted，保留 storage 一段时间后再物理清理
删除不级联修改历史 Task 的 input_file_id 字段；历史记录仍保留 ID，但下载返回 404
```

响应：

```json
{
  "data": {
    "id": "file_xxx",
    "status": "deleted",
    "updated_at": "2026-07-15T11:00:00Z"
  },
  "request_id": "req_xxx"
}
```

### 与其他资源的约束关系

Task 侧 `input_file_id` 的持久化映射边界由 [`ALIGN-001`](待对齐问题.md#align-001) 跟踪；retry / rerun 对已删除输入文件的继承边界由 [`ALIGN-010`](待对齐问题.md#align-010) 跟踪。

```text
input_source = file       时，input_file_id 必填，且对应 SourceFile.purpose 应为 task_input 或 other
script_source = upload    时，source_file_id 必填，且 purpose 应为 bot_script
Schedule.input_file_id 若存在，purpose 应为 schedule_input、task_input 或 other
purpose 在上传成功后不可修改；如需改变用途，必须创建新的 SourceFile
引用不存在、purpose 不匹配或 status != ready 的 file_id 时，创建接口返回 422
```

## Source File 与其他资源的职责边界

Source Files 文档负责文件内容接收、元数据、存储定位、下载鉴权、软删除和引用冲突校验。其他主题文档只定义资源自身的引用字段：

| 使用方 | 局部字段 | Source File 侧校验 |
|---|---|---|
| Job Definition / Job Definition Version | `script_source=upload`、`source_file_id` | `purpose=bot_script`，文件必须为 `ready` |
| Task | `input_source=file`、`input_file_id` | `purpose=task_input` 或允许的通用用途，文件必须为 `ready` |
| Schedule | `input_file_id` | `purpose=schedule_input`、`task_input` 或允许的通用用途，文件必须为 `ready` |

上传文件后，调用方把返回的 `file_id` 作为对应资源的引用；Job Definition、Task、Schedule 不直接接收 multipart 文件内容，也不直接暴露 `storage_key` 或物理路径。
