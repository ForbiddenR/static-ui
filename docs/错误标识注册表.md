## 错误标识注册表

<a id="error-authority"></a>
### 权威边界

| 内容 | 权威归属 |
|---|---|
| REST 失败响应的 `error` / `request_id` 结构 | 本文件 |
| HTTP 状态码与默认 `error.code` 映射 | 本文件 |
| REST、执行、诊断、事件和协议标识的稳定值与命名空间 | 本文件 |
| 已登记标识在具体资源中的业务触发条件和状态影响 | 对应主题文档；不得改变本文件登记的值和跨层分类 |
| REST 成功响应、分页和过滤 | [API约定](API约定.md#rest-conventions) |
| 敏感字段识别和错误信息脱敏 | [安全基线](安全基线.md#sensitive-field-registry) |

新增或修改机器可读错误标识必须先更新本注册表。主题文档中的示例代码若未在本文件登记，不构成可依赖契约；发现差异时登记到 [待对齐问题](待对齐问题.md#alignment-issues)，不得静默选择一方。

### 错误标识命名空间

| 命名空间 | 承载字段 | 用途与外露边界 |
|---|---|---|
| REST API 错误码 | `error.code` | 某次 HTTP 请求失败时供客户端稳定分支；注册表见 [错误标识注册表](错误标识注册表.md#error-registry) |
| 执行错误码 | `Task.error_code`、`TaskItem.error_code`、`TaskFinished.error_code`、`TaskFailed.error_code` | 描述执行结果；可在授权资源详情中读取，不等同于 REST 请求失败 |
| 内部诊断码 | `diagnostic_code` | 记录异常观测，不直接改变资源状态，不作为 REST 错误返回 |
| 内部事件原因 | `task_event.reason` | 说明状态迁移或平台内部事件原因 |
| 协议拒绝原因 | `Welcome.reject_reason`、`TaskAck.reject_reason` | 描述 Worker 会话或一次 assignment 被拒绝的事实 |
| 协议结果枚举 | `CancelResult.result` | 描述取消命令结果，保持小写 wire enum，不属于错误码 |

错误标识规则：

```text
错误码和原因码是稳定机器可读值，已登记值不得静默改变含义
error.message 面向调用方展示，必须按安全基线脱敏
error.detail 只提供按安全基线脱敏后的结构化上下文，客户端不得依赖其文本或未登记结构做稳定分支
人工 retry、Worker retriable 建议、平台自动改派是三个不同概念，不得互相推导
BOT_ID / TASK_ID / TASK_TOKEN 等全大写环境变量不是错误码
```

### 统一错误响应与错误标识注册表

> [本节角色]
> 本节是 REST 错误响应、HTTP 映射以及执行错误、诊断码、事件原因和协议原因分类的统一注册入口。各代码的业务触发条件和状态影响仍以“权威引用”所列章节为准。

所有失败 REST 响应必须使用统一结构：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `error.code` | string | 是 | 稳定机器可读值，必须来自本节 REST 错误码注册表；客户端按此字段分支 |
| `error.message` | string | 是 | 面向调用方的简短说明；敏感字段识别和脱敏以 [安全基线](安全基线.md#sensitive-field-registry) 为准 |
| `error.detail` | object / null | 是 | 按 [安全基线](安全基线.md#sensitive-field-registry) 处理后的字段级或资源级上下文；无上下文时为 `null`，客户端不得依赖未登记的内部结构 |
| `request_id` | string | 是 | 请求关联 ID，用于查询服务端日志和审计记录 |

成功查询得到的 `Task.error_code` 或 `TaskItem.error_code` 是资源执行结果的一部分，仍位于成功响应的 `data` 中，不得因为资源曾执行失败而改用 REST 错误包。

常见 HTTP 状态码：

| 状态码 | 含义 | 默认 REST `error.code` | 示例 |
|---|---|---|---|
| `200` | 查询或操作成功 | — | 获取 Task 详情成功 |
| `201` | 创建成功 | — | 创建 Bot / Task / Schedule 成功 |
| `400` | 请求格式错误 | `INVALID_REQUEST` | JSON 解析失败、字段类型不对 |
| `401` | 未认证 | `UNAUTHENTICATED` | 未登录或 token 失效 |
| `403` | 无权限 | `FORBIDDEN` | 没有运行 Bot 或取消 Task 的权限 |
| `404` | 资源不存在或按安全策略不可见 | `RESOURCE_NOT_FOUND` | task_id 不存在 |
| `409` | 状态或唯一性冲突 | `STATE_CONFLICT` | 终态 Task 不能取消、重复 code |
| `413` | 请求实体超过平台大小限制 | `PAYLOAD_TOO_LARGE` | 上传文件超过允许大小 |
| `422` | 请求格式正确但业务输入校验失败 | `INVALID_INPUT` | cron 非法、input_source 与输入字段不匹配 |
| `500` | 系统内部错误 | `INTERNAL_ERROR` | 数据库或存储异常 |

<a id="rest-errors"></a>
### A. 对外 REST 错误码

| `error.code` | HTTP | 适用场景 | 对外可见性 | 调用方处理建议 |
|---|---:|---|---|---|
| `INVALID_REQUEST` | `400` | JSON 无法解析、字段类型错误、请求格式不符合协议 | 对外 | 修正请求格式后重新提交 |
| `UNAUTHENTICATED` | `401` | 缺少认证信息、会话或访问令牌失效 | 对外 | 重新认证或刷新有效凭据后重试 |
| `FORBIDDEN` | `403` | 已认证，但当前主体无权访问资源或执行动作 | 对外 | 不应原样重试；申请权限或更换有权限主体 |
| `RESOURCE_NOT_FOUND` | `404` | 资源不存在，或按安全策略对当前主体不可见 | 对外 | 核对资源 ID 和可见范围 |
| `STATE_CONFLICT` | `409` | 当前资源状态不允许动作，或唯一性约束冲突 | 对外 | 刷新资源状态或修改冲突输入后再决定是否重试 |
| `PAYLOAD_TOO_LARGE` | `413` | HTTP 请求体或上传文件超过平台配置的大小限制 | 对外 | 减小请求体或文件后重新提交 |
| `INVALID_INPUT` | `422` | 请求格式正确，但字段组合、业务约束或引用资源不满足要求 | 对外 | 根据 `error.detail` 修正输入后重新提交 |
| `BOT_VERSION_REQUIRED` | `422` | Bot 操作要求 current version，但 `current_version_id` 为空 | 对外 | 创建并发布 BotVersion 后重新执行操作；权威流程见 [Bot API](Bot规范.md#bot-api) |
| `INTERNAL_ERROR` | `500` | 未预期的平台内部异常 | 对外；只返回脱敏信息 | 可使用同一 `request_id` 排障；是否重试由调用方策略决定 |

REST 错误码扩展规则：

```text
新的对外 error.code 必须先在本表注册 HTTP 映射、适用范围和处理建议
资源专属错误码优先表达稳定业务条件；未登记专属码时使用对应 HTTP 的通用码
不得把 Task.error_code、diagnostic_code、task_event.reason 或 gRPC 原因码直接作为 REST error.code
同一 error.code 不得同时映射多个互相冲突的 HTTP 语义
```

<a id="execution-errors"></a>
### B. 已持久化的执行错误码

| 代码 | 产生者 / 写入位置 | 触发事实与状态影响 | 授权外露方式 | retry 边界 | 权威引用 |
|---|---|---|---|---|---|
| `SCRIPT_EXIT_NONZERO` | Master 写入 `Task.error_code` | 脚本有正常退出码但 `exit_code != 0`，且 Worker 未提供更具体的已注册执行错误码；Task=`failed` | Task 详情 | 可按 [Task API](Task执行规范.md#task-api) 人工创建新 Task；不代表自动重试 | [Task 状态机](Task执行规范.md#task-status)、[Task API](Task执行规范.md#task-api) |
| `ITEMS_NOT_FINALIZED` | Master 写入 `Task.error_code` | 脚本 exit 0，但聚合后仍存在 `pending` / `running` TaskItem，Task=`failed` | Task 详情 | 同上 | [Task 状态机](Task执行规范.md#task-status) |
| `UNEXPECTED_CANCELED_ITEMS` | Master 写入 `Task.error_code` | 非取消流程中出现 canceled TaskItem，Task=`failed` | Task 详情 | 同上 | [Task 状态机](Task执行规范.md#task-status) |
| `WORKER_OFFLINE` | Master 写入 `Task.error_code` | 执行中的 Worker 离线，Task=`failed` | Task 详情 | 同上；本表不定义自动恢复或改派 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `SCRIPT_START_FAILED` | Worker 通过 `TaskFailed.error_code` 上报，Master 写入 Task | Worker 无法拉起脚本进程，Task=`failed` | Task 详情；协议内可见 | Worker 可提供 `retriable` 建议，但第一版不据此自动改派 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `RUNTIME_CRASH` | Worker 通过 `TaskFailed.error_code` 上报，Master 写入 Task | Runtime 异常崩溃且没有正常完成，Task=`failed` | Task 详情；协议内可见 | 同上 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `INPUT_DOWNLOAD_FAILED` | Worker 通过 `TaskFailed.error_code` 上报，Master 写入 Task | Worker 本地准备输入文件失败，Task=`failed` | Task 详情；协议内可见 | 同上 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `ITEM_NOT_FINALIZED` | SDK / Runtime 写入 `TaskItem.error_code` | `task_item.run(...)` 无异常退出但未显式设置终态，SDK 将该 Item 标记 `failed` | TaskItem 详情 | Item 不支持原地重试；是否创建新 Task 见 [Task API](Task执行规范.md#task-api) | [Runtime / SDK](Worker协议与运行时.md#runtime-sdk) |

`ITEM_NOT_FINALIZED` 与 `ITEMS_NOT_FINALIZED` 属于不同资源层级：前者是单个 TaskItem 已被 SDK 收敛为 `failed`；后者是 Master 裁定 Task 时仍发现未进入终态的 TaskItem。二者不得互相替换，也不自动从 Item 级传播为 Task 级错误码。

执行错误码扩展规则：

```text
TaskFinished / TaskFailed 上报的 error_code 必须是 Worker 与 Master 都能识别的执行错误码
未知执行错误码可以保留原值并按通用失败处理，但必须记录产生方和原始上下文
执行错误码是否允许人工 retry 不能覆盖 [Task API](Task执行规范.md#task-api) 的 Task 状态资格
TaskFailed.retriable 只是 Worker 建议，不等于平台自动改派或 REST retry 承诺
```

<a id="diagnostic-and-protocol-codes"></a>
### C. 内部诊断、事件原因与协议枚举

| 命名空间和值 | 类型 | 含义与状态影响 | 外露与重试边界 | 权威引用 |
|---|---|---|---|---|
| `diagnostic_code=STATISTICS_MISMATCH` | 内部诊断码 | Worker 统计与 Master 数据库聚合不一致；以 Master 聚合为准，不设置 Task 错误码，不改变 Task 终态 | 仅内部日志或事件 metadata | [Task 状态机](Task执行规范.md#task-status) |
| `task_event.reason=DISPATCH_TIMEOUT` | 兼容事件原因 | 旧实现对 Ack / Started 派发超时的汇总值；新实现分别使用 `ACK_DEADLINE_EXPIRED`、`START_DEADLINE_EXPIRED` | 不是 Task `timeout`，不作为 REST 或执行错误码 | [Task 状态机](Task执行规范.md#task-status) |
| `task_event.reason=DISPATCH_RESERVED` | 内部事件原因 | Master 已建立 assignment 和 dispatch reservation，Task 进入 `dispatching` | 不代表 Worker 已 Ack 或 Started | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=TASK_ACK_ACCEPTED` | 内部事件原因 | 当前 assignment 已被 Worker 接受，仍保持 `dispatching` 并占用 reservation | 不进入 `running` | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=TASK_ACK_REJECTED` | 内部事件原因 | Worker 拒绝当前 assignment；Master 回收并重新入队 | 不写 Task 执行错误码 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=ACK_DEADLINE_EXPIRED` | 内部事件原因 | 未及时收到合法 accepted TaskAck；回收 assignment | 不是 Task `timeout` | [Task 状态机](Task执行规范.md#task-status) |
| `task_event.reason=START_DEADLINE_EXPIRED` | 内部事件原因 | accepted 后未及时收到合法 TaskStarted；回收 assignment | 不是 Task `timeout` | [Task 状态机](Task执行规范.md#task-status) |
| `task_event.reason=NO_CANDIDATE_WORKER` | 内部事件原因 | 当前没有匹配且有容量的 Worker；Task 保持 `pending` 并退避 | 不增加 dispatch attempts，不自动 failed | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=DISPATCH_REQUEUED` | 内部事件原因 | 派发前 assignment 回收后重新进入 pending 队列 | 新派发必须使用新 assignment | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=DISPATCH_ATTEMPTS_EXHAUSTED` | 内部事件原因 | 达到自动派发次数上限，Task 仍为 pending 并暂停自动派发 | 等待人工恢复，不写执行错误码 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=WORKER_OFFLINE_RECLAIM` | 内部事件原因 | dispatching Worker offline，回收尚未 Started 的 assignment | running offline 仍使用 `WORKER_OFFLINE` 执行错误 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=WORKER_DISABLED_RECLAIM` | 内部事件原因 | Worker disable 后回收尚未 Started 的 assignment | 不影响 running / canceling Task | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=ASSIGNMENT_ABORT_REQUESTED` | 内部事件原因 | Master 已要求 Worker 停止或禁止启动失效 assignment | 不是用户取消 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=RECONCILIATION_ABORT` | 内部事件原因 | 重连对账发现未知、旧或已终态 assignment，要求 Worker abort | 不恢复既有终态 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `task_event.reason=DISPATCH_MANUALLY_RESUMED` | 内部事件原因 | 运维显式恢复 pending Task 的自动派发 | 与终态 retry 不同 | [Task API](Task执行规范.md#task-api) |
| `diagnostic_code=HEARTBEAT_CAPACITY_CONFLICT` | 内部诊断码 | Heartbeat 容量字段互相冲突；Master 使用最保守值 | 不直接改变 Task 状态 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `diagnostic_code=UNKNOWN_TASK_ACK_REJECTION` | 内部诊断码 | Worker 使用未登记或空的 TaskAck reject reason | 仍按拒绝回收，不写执行错误码 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `TaskAck.reject_reason=NO_FREE_SLOT` | 协议拒绝原因 | Worker 暂无空闲执行槽位，拒绝当前 assignment | 协议和授权运维信息可见；不直接写 Task 执行错误 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `TaskAck.reject_reason=RUNTIME_NOT_SUPPORTED` | 协议拒绝原因 | Worker 不支持 Task 要求的 runtime | 同上；后续调度行为不由本表定义 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `TaskAck.reject_reason=WORKER_DISABLED` | 协议拒绝原因 | Worker 已被禁用，拒绝当前 assignment | 同上；可用于 Master 匹配与 Worker 接收之间的状态竞态 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `CancelResult.result=canceled` | 协议结果枚举 | Worker 已完成取消 | 保持小写 wire enum，按 [Worker 协议](Worker协议与运行时.md#worker-protocol) 对账，不转成错误码 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `CancelResult.result=force_killed` | 协议结果枚举 | Worker 在宽限期后强制终止进程 | 同上 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `CancelResult.result=already_finished` | 协议结果枚举 | Task 已先完成，取消不覆盖已有终态 | 同上 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |
| `CancelResult.result=not_found` | 协议结果枚举 | Worker 找不到本地运行实体，Master 按现有状态对账 | 同上 | [Worker 协议](Worker协议与运行时.md#worker-protocol) |

`Welcome.reject_reason` 属于 Worker 会话拒绝命名空间，与 `TaskAck.reject_reason` 不共享业务含义。第一版尚未登记固定 Welcome 拒绝值；重连对账和 Abort 原因的稳定集合也尚未统一，这些边界由 [`ALIGN-009`](待对齐问题.md#align-009) 跟踪。实现可以记录未知值用于兼容和排障，但在形成跨实现稳定依赖前必须先补充本注册表。

`ScheduleRun.reason` / `ScheduleRun.error_code` 当前不属于上表任何已闭环命名空间，其稳定注册边界由 [`ALIGN-014`](待对齐问题.md#align-014) 跟踪；不得直接复用 REST 或 Task 执行错误码。

“retry”相关术语必须区分：

```text
人工 retry                 用户按 [Task API](Task执行规范.md#task-api) 从允许的 Task 终态创建新 Task
人工 resume-dispatch       运维按 [Task API](Task执行规范.md#task-api) 恢复同一个 pending Task 的自动派发，不创建新 Task
retriable 建议              Worker 在 TaskFailed 中提供的异常可恢复性建议，第一版只记录
平台派发前自动改派 / 重派  仅限合法 TaskStarted 之前，规则见 [Worker 调度规则](Worker协议与运行时.md#worker-dispatch)
平台执行后自动重试         第一版不实现；不得由 retriable 自动触发
```
